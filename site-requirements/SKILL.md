# Site Requirements

対象サイトの要件を `REQUIREMENTS.md` に書いて止まる。コード、スタイル、コンポーネントの変更はしない。

実装は別ターン。ユーザーが `REQUIREMENTS.md` を指定して頼んだとき、そのリポジトリのコンポーネントと、見た目用の skill（`frontend-design`、必要なら `baseline-ui`）に従う。この skill は実装手順を持たない。

## 進め方

1. 対象リポジトリの構成、既存ページ、コンポーネント、スタイルの入口を自分で見る。ファイルから分かることは聞かない
2. 下の設計ツリーをラウンドで聞く
3. 全部聞き終わったら要件を短く復唱し、共有できたか確認する
4. 本人が「それで」と認めてから、対象リポジトリに `REQUIREMENTS.md` を書く。置き場所の指定があればそこに従う
5. 書いたパスを伝え、実装はこの skill ではしないと一言添えて終わる

確認前に `REQUIREMENTS.md` を書かない。認めたあともコードは書かない。

## 質問の出し方

設計ツリーとして扱う。前提が揃っている質問だけを、そのラウンドでまとめて出す。一度に全部聞かず、次のラウンドは答えを受け取ってからにする。

各質問はこの形にする。

```
❓ **Q1** - **<項目>**: <本文。選択肢があれば列挙>

➡️ <あなたが勧める答え>
```

勧める答えは、見たファイルと矛盾しない具体案にする。
ユーザーが「おまかせ」「それで」と言ったら、そのラウンドの推奨案を採用して次へ進む。
載せたくない項目はスキップしてよい、と毎回短く添える。

## 設計ツリー

### ラウンド 1（土台。互いに独立）

- 誰が開くか
- このページの仕事（何を理解して、次に何をしてほしいか）
- 触る範囲と、触らない範囲
- トーン（明暗、落ち着き / 派手）。既存の色や字を残すかもここに含める

技術スタック、フレームワーク、ファイル構成は自分で見て決める。ユーザーに聞かない。

### ラウンド 2（ラウンド 1 のあと）

- 最初の画面に出すもの
- セクションの並び
- 既存の部品で残すもの、見た目だけ変えるもの

ラウンド 2 のあと、まだ曖昧な枝だけラウンド 3 で潰す。聞くことがなくなったらヒアリング終了。

## REQUIREMENTS.md の形

実装が迷わないことだけ書く。色の hex、クラス名、使うコンポーネント名は書かない。それらは実装ターンがリポジトリを見て決める。

```markdown
# サイト要件

- 誰向け:
- ページの仕事:
- 触る範囲:
- 触らない範囲:
- 最初の画面:
- セクション:
- トーン:
- 残すもの:
```

## 終わったあとの手渡し

同じチャットでも、この skill のターンでは実装を始めない。
ユーザーが実装を頼んだら、`REQUIREMENTS.md` を読み、対象リポジトリの既存コンポーネントとスタイルに合わせる。見た目の方向は `frontend-design`、Tailwind の既存 UI を磨くときだけ `baseline-ui` を使う。
